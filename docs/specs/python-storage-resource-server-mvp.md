# Python Storage Resource Server MVP — Approved Design Specification

**Status:** User-approved Storage RBAC direction; independent security and cross-repository contract reviews of the substantive draft are complete (see Storage issue #18). This design is not ready-for-agent; no production service source has been added. The reviewed snapshot SHA-256 is recorded in the linked issue/ADR; any material contract or security edit requires a focused rerun.

**Canonical path:** `docs/specs/python-storage-resource-server-mvp.md`.

## 1. Repositories and boundaries

- `decent-simple-storage` owns the Python Storage Resource Server, its SQLite/filesystem backend, Storage API, provider policy and consumer acceptance suite.
- `decent-keycloak` owns Keycloak token issuance and native client-role configuration. For the accepted Storage-facing profile, Keycloak issues its ordinary access token with the single Storage audience and operator-assigned Storage client roles; it does not issue `storage_authorization` or `storage_identity`, and does not perform prompt-revocation. Storage maps the exact `(iss, sub)` to its raw Registry owner through an operator-reviewed, audited one-to-one mapping. Keycloak issue #56 remains open for broader architecture and implementation gates; implementation is not authorized by this reconciliation. Storage has no Keycloak SDK/Admin API dependency and makes no AS callback. Storage itself validates enrollment JWS proofs and current Registry identity at submission; Keycloak does not proxy enrollment.
- `decent-ecosystem`'s adopted semantic-v1 grant package remains unchanged. It describes existing-object grant semantics; create/enrollment are separate Storage-owned profiles. RFC 9068 output-token conformance is not claimed.
- Issue #18 remains open for contract reconciliation. Issue #1 in `decent-simple-storage` is the Python service-spec home. The Storage-facing role profile is accepted narrowly; the broader owner-signed envelope and WordPress decisions in Keycloak ADR 0001 remain proposed. Keycloak issue #56 remains open and authorizes no implementation. This does not change the adopted ecosystem semantic-v1 package or claim ecosystem qualification. The user-selected digest-uniqueness change is recorded in Storage issue #1 and as superseding comments on closed #6/#10.

## 2. Adopted decisions

- Python Storage Resource Server in this repository; Keycloak-issued ordinary OIDC access tokens with native client roles for Storage authorization. No custom Java Storage SPI is specified by this profile.
- SQLite for metadata, quota ledger, enrollment, nonce/replay and idempotency state; local filesystem for blob bytes; one service node only. No HA or multi-node storage claim.
- Operator enrollment/quota decisions use a local operator-only CLI; no public admin HTTP API.
- Owner-scoped server-generated opaque object IDs; owner is the raw Registry identity reached through the active exact `(iss, sub)` mapping, never a request field.
- The service accepts generic Storage Objects and role-authorized site-specific JSON Account Entities; both use only `application/json` in this release. There is one site-specific entity per owner and canonical HTTPS site origin; distinct origins remain separate even under one operator. The Master Account Entity is wallet-owned and outside this service's object/profile model: it exists only within the existing authenticated wallet-container v2 payload and must never be accepted, stored, returned, discovered, or replicated by Storage, including as ciphertext. There is no separate Master-record key/envelope or Storage upload path. Storage does not create a plaintext Master entity, and full issue #12 conformance is not claimed. Plaintext site-specific entities are visible to the provider/operator; the provider profile must disclose this and makes no at-rest privacy promise.
- Site-specific entities are snapshots classified by caller-supplied, syntactically validated metadata. `site_origin` is not an authorization boundary or evidence of owner consent. Master-to-site copying, automatic propagation and synchronization are out of scope. Because of the selected digest uniqueness rule, identical bytes cannot be retained as separate site-entity objects for the same owner; a conflicting second create is rejected.
- `storage:read` permits reading the complete current JSON object owned by the mapped Registry identity. `storage:update` permits a structurally valid full replacement subject to `If-Match` and local policy; there are no per-object JSON Pointer grants.
- An owner's exact content digest may be retained under only one logical object. A second logical object with the same owner+digest is rejected. Cross-owner copies remain independent.
- The owner's quota-downgrade policy is resolved in favor of issue #10's full-reservation invariant: reserve the full new unique payload while old bytes remain charged; do not use replacement credit. If old+new exceed the reduced quota, reject even when the final atomic replacement would decrease retained bytes. This intentionally narrows issue #10's separate non-increasing-write allowance for this Storage profile; it is not a semantic-v1 or ecosystem-wide change.
- Create requires the operator-assigned `storage:create` role and explicit Storage metadata headers; no owner-signed per-object create grant or precomputed content-digest consent is required. Exact operation retries remain idempotent; changed bytes under the same idempotency key are rejected.
- Access tokens use Keycloak's native `resource_access.<storage-client-id>.roles` array with a closed Storage-owned role vocabulary. Storage accepts normal issuer expiry and refresh behavior, imposes no additional maximum token lifetime, and does not support prompt-revocation/RFC 7662 for this profile. Role removal or withdrawal does not revoke a previously issued token before its `exp`; Storage promises no maximum revocation delay.
- Enrollment uses a separate one-use Ed25519 compact JWS bound to the exact owner, provider, current Registry key/sequence, nonce, `iat` and `exp`.
- Preserve object ownership by the exact raw Registry owner identifier resolved from an audited one-to-one mapping for configured issuer and exact `(iss, sub)`. Never infer this mapping from email, aliases, or key equality. Site/client values and `Origin` are not authorization evidence in this profile.

## 3. Keycloak Storage RBAC token profile (Storage-owned)

The accepted Storage-facing Keycloak profile uses an ordinary signed Bearer access token and native operator-assigned client roles. It does not use an RFC 7523 Storage grant, `storage_authorization`, `storage_identity`, or any grant-derived claim. Keycloak's ordinary access-token expiry and refresh behavior applies. Storage imposes no additional maximum token lifetime and makes no maximum revocation-delay guarantee: role removal, enrollment withdrawal, or account changes do not invalidate an already-issued token before its signed `exp`. This is deliberate and must be disclosed to operators; prompt revocation/RFC 7662 is unsupported for this profile.

Verify access tokens only against the configured issuer and trusted JWKS; never follow token-supplied issuer/key URLs. Require the configured exact `iss`, a valid signature under the configured asymmetric algorithm/key type, exact single-value `aud` equal to the configured Storage resource client, exact nonempty `sub`, and safe-integer `exp`/`iat` (and `nbf` when present) within configured clock skew. Reject ID tokens and tokens with missing, malformed, expired, or not-yet-valid temporal claims, duplicate JSON member names, or unsupported JOSE headers. A token-supplied `azp`, OAuth client ID, site origin, or request header is not an authorization input. Read role strings only from `resource_access.<configured-storage-client-id>.roles`; do not accept realm roles, similarly named claims, or another client's role entry. An absent Storage-client role entry or absent `roles` member is an empty role set and therefore cannot satisfy any route (403 `insufficient_scope`); if present, `roles` must be a unique string array containing only the closed Storage vocabulary below. Malformed arrays or any duplicate/unknown Storage-client role reject the token (401 `invalid_token`), even if a known role is also present. Configure trusted issuer/JWKS, allowed algorithms, clock skew, and bounded JWKS refresh/cache behavior. On required JWKS unavailability fail closed with `503`; a valid refreshed JWKS that lacks the key rejects the token with privacy-safe `401 invalid_token`. This is a project token profile, not RFC 9068 conformance.

### Storage client roles and subject-to-owner mapping

| Role | Authorized operation |
|---|---|
| `storage:read` | Read the complete current JSON object for the mapped owner. |
| `storage:create` | Create an object for the mapped owner, subject to local enrollment/quota and metadata rules. |
| `storage:update` | Replace the complete current JSON object for the mapped owner, subject to `If-Match`, structural validation, and local policy. |
| `storage:delete` | Retire an object for the mapped owner, subject to lifecycle and local policy. |
| `storage:enrollment:read` | Read only the mapped owner's enrollment status. |
| `storage:enrollment:withdraw` | Withdraw only the mapped owner's enrollment. |

Roles are assigned and removed by the Keycloak realm/resource operators; the wallet provider does not grant roles. A role applies to every object owned by the mapped Registry identity, without per-object digest, purpose, site/client, consent-expiry, or JSON Pointer restriction. Storage still enforces object ownership, local enrollment/lifecycle rules, quota admission for creates and writes, JSON validity, idempotency, and concurrency safeguards; reads and deletes do not require remaining quota. `storage:read` returns the full current object; `storage:update` permits any structurally valid full replacement, with `If-Match` required. There is no cross-owner access. Unknown or duplicate roles under the configured Storage client fail closed even if a known role is also present.

For each configured issuer, maintain an operator-reviewed, audited, one-to-one active mapping between exact `(iss, sub)` and the exact raw Registry owner identifier: one subject per owner and one owner per subject for that issuer. The mapping selects the existing Storage owner key; it does not normalize or replace it. Mapping creation occurs as part of enrollment approval after the operator verifies the Keycloak subject against the enrolled Registry identity. Missing, inactive, ambiguous, or conflicting mappings fail closed. Remapping or deactivation requires an explicit audited operator action; email, aliases, and key equality are never automatic linking evidence. Object ownership checks use the mapped raw Registry identifier, not a caller-supplied value.

Keycloak role tokens are resource-wide and site-independent. The Storage resource audience and role claim are the authorization inputs; requesting-client claims, site origin, and `Origin` do not grant or restrict access. Site-specific entity origin is metadata only as specified in §4.

### Superseded: prior RFC 7523 outer Storage grant

The following §§3.1–3.2 describe the former owner-grant contract for historical traceability only. They are superseded and are not requirements of the adopted Keycloak Storage RBAC profile. They do not alter the separate adopted semantic-v1 package.

#### Historical outer-assertion Storage context (not normative)

When semantic-v1 actions include `read`, the signed outer claims also contain exactly `storage_disclosure: {wire_version:1, json_pointers:[...]}`. It is omitted otherwise. When actions include `update`, also contain exactly `storage_update_context: {wire_version:1, retention_mode, json_write_pointers:[...]}`; omitted otherwise. Arrays are nonempty, unique strings, parsed as RFC 6901 pointers and bounded by the advertised provider limits; root pointer `""` is explicit whole-object scope. Reject unknown properties/versions and conditional-claim mismatches. These context claims are signed by the same owner-key JWS, are not `decent_grant.extensions`, and cannot alter semantic-v1. Keycloak verifies `site_origin`/`client_id` against the authenticated OAuth client and configured mapping, then emits one normalized `storage_authorization` object. For create assertions, `storage_site_context` is required but disclosure/update contexts are forbidden.

#### Historical `storage_authorization` and `storage_identity` profiles (not normative)

The claim is one JSON object with no unknown members. Conditional members must be present exactly when their action/profile requires them; do not silently ignore malformed scope.

| Member | Requiredness and validation |
|---|---|
| `profile_version` | Required integer, exactly `1`. |
| `grant_type` | Required enum `existing_object` or `create`. |
| `owner_identifier` | Required exact UTF-8 string, 1–512 characters; must equal JWT `sub`. |
| `storage_aud` | Required exact configured Storage resource-client ID, 1–512 characters; for Keycloak prompt-revocation this is the confidential client that authenticates introspection. JWT `aud` must be that single value only. |
| `site_origin` | Required canonical HTTPS origin from the signed `storage_site_context`; must match configured mapping for `client_id`. |
| `client_id` | Required exact OAuth client ID from authenticated grant request; equals the top-level token `client_id`. |
| `owner_key_fingerprint` | Required `sha256:` plus lowercase hex SHA-256 of the 32-byte current Ed25519 public key. |
| `identity_registry_seq` | Required positive safe-integer sequence of the current Registry binding verified at issuance. |
| `storage_object_digest` | Required `sha256:` plus 64 lowercase hex characters; exact stored/requested version or expected create bytes. |
| `storage_actions` | Required unique array of 1–8 semantic-v1 action strings. Existing-object profile recognizes only `read`, `update`, `delete`; create profile requires exactly `create`. Unsupported strings/actions deny. |
| `storage_purpose` | Required exact opaque string, 1–128 characters. |
| `wallet_grant_jti` | Required exact assertion `jti`, nonempty and at most 256 characters. |
| `wallet_consent_exp` | Required positive safe-integer Unix seconds; output token `exp` cannot exceed it. |
| `object_kind` | Required only for `create`; enum `generic_json` or `site_account_entity`. Persist with the object. |
| `json_pointers` | Required iff `read` is present. Nonempty unique RFC 6901 pointer array; the zero-length root pointer is explicit whole-object read. Count/length are bounded by required operator-configured limits. |
| `json_write_pointers` | Required iff `update` is present. Nonempty unique RFC 6901 pointer array; root pointer means whole-object replacement. Count/length are bounded by required operator-configured limits. |
| `retention_mode` | Required iff `update` is present; enum `atomic` or `versioned`, copied only from signed `storage_update_context`. |

Under the superseded owner-grant profiles only, standard token `iss`, `sub`, single-value `aud`, `iat`, `exp`, and `jti` were required, with `nbf` validated when present. The former profile rejected malformed/duplicate JSON members, unsafe numeric values, unknown fields/versions, inconsistent standard/custom claims, unsupported `alg`/key type, and token expiry outside its configured clock-skew/max-lifetime policy. Its `storage_identity` variant required per-request Registry resolution for enrollment status/withdrawal. None of those grant-profile or identity-token rules add requirements to the adopted native-role profile; the active token rules are in §3.

#### Historical enrollment-only identity token (`storage_identity`; not normative)

**Historical only:** this separate identity-token profile is superseded and is not required by the adopted Storage role profile. The active replacement uses the ordinary role-bearing access token, `storage:enrollment:read` or `storage:enrollment:withdraw`, and the active exact `(iss,sub)` mapping; it requires neither `storage_identity` nor fresh wallet authentication for these routes.

Enrollment status and withdrawal use a separate issuer-signed Storage identity token, not `storage_authorization`. It is issued after fresh wallet authentication and current Registry identity/key verification, independently of Storage enrollment state and quota; therefore an owner can inspect or withdraw enrollment while not enrolled, suspended, or revoked. Require the same configured `iss`, strict JOSE header and trusted JWKS rules as §3; exact single `aud == storage_aud`; `exp`, `iat`, `jti`; top-level trusted `client_id`; and an exact `storage_identity` object with `profile_version` integer 1, `owner_identifier` string (1–512 exact characters), canonical `site_origin`, `client_id` string (1–512 exact characters), `owner_key_fingerprint` (`sha256:` plus 64 lowercase hex characters), and positive safe-integer `identity_registry_seq`. No unknown or duplicate members. Top-level claims are the standard JWT fields allowed by §3 plus `client_id`, `storage_site_context`, and `storage_identity`; reject `storage_authorization` and all other custom claims. Require `sub == storage_identity.owner_identifier`, top-level `client_id == storage_identity.client_id == storage_site_context.client_id`, `storage_identity.site_origin == storage_site_context.site_origin`, and the exact owner-signed `storage_site_context` profile from §3.1. The issuer must derive `client_id` from the authenticated OAuth client and validate the owner signature/context before issuing; Storage validates the signed claim equalities and never trusts request headers for this binding. This profile omits `storage_authorization` entirely and carries no object ID, digest, actions, purpose, or disclosure/write pointers. It must not authorize any object route or content operation; its only permitted routes are `GET /v1/enrollments/me` and `DELETE /v1/enrollments/me`. It has a required operator-configured short maximum lifetime, no refresh token, and uses the same `storage_aud` resource-client ID as other Storage tokens. On each status/withdrawal request, Storage resolves the current Registry identity and requires exact owner key fingerprint and sequence match; mismatch denies with privacy-safe 401, and Registry unavailability fails closed with 503. Enrollment state itself is not required to issue or validate this identity-only token.

## 3.3 HTTP and provider-profile wire contracts

All successful API responses are UTF-8 JSON. Errors use a fixed RFC 9457-style `application/problem+json` body with only `type`, `title`, `status`, stable machine `code`, and opaque `request_id`; never include owner, token, site, object, pointer or content values. `Idempotency-Key` is required for every mutation, ASCII visible characters only, 1–128 bytes; scope and exact-retry semantics are defined in §5. `If-Match` is one quoted strong ETag whose opaque value is `sha256:<64 lowercase hex>`; weak, wildcard, list and unquoted values are rejected.

| Response | Exact members |
|---|---|
| Enrollment challenge `201` | `storage_aud` string, `nonce` base64url string, `expires_at` integer Unix seconds. |
| Enrollment submission `202` | `request_id` opaque string, `state` exactly `pending`. |
| Enrollment status `200` | `state` exactly `approved`, `suspended`, `revoked`, or `withdrawn`; `policy_version`; `decided_at` and `reason` only if present for that state; `quota_bytes` only while approved. Only owners with an active subject mapping can call this route; pending, rejected, and never-approved owners have no mapping and cannot query status. |
| Create/update `201`/`200` | `object_id`, `digest` (`sha256:` format), `byte_count`, `object_kind`, current-object `provider_url`, and `provider_profile_url`. |
| Read `200` | `object_id`, current-version `digest`, and the complete JSON object `value`; no extra members. |
| Delete `204` | No body. |

The public `decent-storage-provider.json` has exactly these top-level members: `profile_version` (integer 1); `storage_aud` (exact 1–512 character resource string); `endpoints` (object with exactly `objects`, `enrollment_challenges`, `enrollments`, `provider_profile`, each an absolute HTTPS URL); `accepted_media_types` (array containing exactly the string `application/json`); positive integer `max_request_bytes`, `max_token_bytes`, `max_json_depth` (1–64), `max_json_nodes` (positive and no greater than `max_request_bytes`); `quota_basis` (`retained_payload_bytes`); `dedup_scope` (`owner`); positive integer `versioned_retention_seconds` (the fixed duration for which prior versions are retained when `Storage-Retention-Mode: versioned` is selected); `quota_downgrade_policy` (`grandfather_existing_full_reservation`); `revocation_profile` exactly `normal_expiry`; `topology` (object with exactly `deployment=single_node`, `blob_backend=filesystem`, `metadata_store=sqlite`, `replication=none`); `at_rest_encryption` (object with exactly `application_level=none`, `volume_encryption_status=enabled|disabled|unknown`, `managed_by=operator_or_provider`); `backup` (object with exactly boolean `enabled`, nullable positive integer `cadence_seconds`, nullable positive integer `retention_seconds`, nullable positive integer `maximum_deletion_lag_seconds`, nonempty `restore_test_expectation`, and `deletion_journal` object with exactly `mode` (`none|off_host_append_only`), `independent_failure_domain` (boolean), `retention` (`none|deployment_lifetime`), and `restore_requires_fresh_head` (boolean); when backup is disabled, the three numeric fields are null, expectation is `not_applicable`, and journal fields are `none,false,none,false`; when enabled, journal fields are `off_host_append_only,true,deployment_lifetime,true`); and `deletion` (object with positive `active_copy_purge_max_seconds`, `backup_restore_prohibited=true`, and `secure_erasure=false`). No unknown members. `active_copy_purge_max_seconds` bounds removal/unavailability of provider-controlled active blob copies after logical retirement. `backup.maximum_deletion_lag_seconds` bounds the time from retirement until every provider-controlled backup containing retired bytes expires or is removed; it includes backup retention, is independent of active-copy purge, and is null only when backups are disabled. A restore must apply a monotonic deletion-tombstone journal newer than the selected backup before serving; if the journal is unavailable or incomplete, keep the service offline. Providers unable to guarantee this must disable backups. The profile expressly makes no secure-erasure promise and excludes Registry history, caches, previously downloaded copies, consumer copies, and third-party replicas outside provider control. The provider profile discloses that site Account Entity JSON is plaintext to the operator and that the service adds no application-layer encryption. All limits and durability/deletion facts are configured and published; missing disclosure prevents startup. Do not publish an RPO/RTO unless substantiated. The only supported revocation profile is `normal_expiry`; there is no prompt-revocation mode to enable or silently downgrade. Role changes affect newly issued/refreshed tokens under issuer policy; already-issued tokens remain valid until `exp`.

## 4. Enrollment and object creation profiles

### Enrollment

- `POST /v1/enrollment-challenges` takes `{}` and returns 201 with a 32-byte random nonce encoded as unpadded base64url, exact `storage_aud`, and integer `expires_at`. Store only a cryptographic hash of the nonce; bind it to this provider and expiry. Challenge lifetime, outstanding-count caps per IP/global bucket, and rate limits are required operator settings. Challenge creation is intentionally not idempotent; each retry creates a fresh expiring challenge.
- `POST /v1/enrollments` accepts a compact Ed25519 JWS body with `Content-Type: application/jwt` and a required `Idempotency-Key`; no Keycloak access token or Storage role is required. This owner proof is independently validated against the current Registry identity/key and remains the authority for enrollment submission. Require `Content-Length`; the proof's encoded bytes must be no greater than both `max_request_bytes` and `max_token_bytes`, otherwise return `413 content_too_large` before parsing. Its decoded protected-header and payload JSON must satisfy `max_json_depth` and `max_json_nodes`, otherwise return `413 content_too_complex`. Protected header contains exactly `typ=decent-storage-enrollment+jwt`, `alg=EdDSA`. Strict payload fields: `profile_version:1`, exact `owner_identifier`, exact `storage_aud`, `nonce`, unique `jti`, safe-integer `iat`, `exp`, `owner_key_fingerprint` (`sha256:` plus lower-case hex SHA-256 of the 32-byte key), and positive safe-integer `identity_registry_seq`. No unknown fields, duplicate JSON members, unsafe timestamps, cross-protocol type, wrong audience, stale key/sequence, or reused nonce/JTI are accepted. A malformed JWS, malformed claims, or invalid proof signature within limits returns `400 invalid_request`; a valid-shape proof with stale or mismatched current Registry identity/key/sequence also returns `400 invalid_request` without consuming its nonce/JTI. A replayed nonce/JTI not matched to the same completed idempotent request returns generic `409 conflict`. The enrollment JWS is not an Authorization Bearer token and never uses the `401 invalid_token` mapping. Enrollment `jti` is unique within this Storage instance across all owners and enrollment proofs; persist its consumption at least through proof expiry plus configured clock skew and never permit an exact replay to create another enrollment. Require `iat` within configured skew, `exp > now`, `exp-iat` within configured maximum, and `exp <= challenge expiry`. Resolve the current Registry identity/key and verify the signature before consuming nonce/JTI.
- Successful proof creates `pending` enrollment only; it never approves quota. Respond 202 with request ID and state. The only allowed transitions are `pending -> approved|rejected|withdrawn`, `approved -> suspended|revoked|withdrawn`, `suspended -> approved|revoked|withdrawn`, `rejected -> withdrawn`, and `revoked -> withdrawn`; `withdrawn` is terminal. Rejection and revocation are terminal for eligibility; an owner in either state cannot re-enroll or obtain a new enrollment record in this MVP. Withdrawal never releases the owner's one-active-enrollment slot: the owner slot and terminal withdrawn record are permanent; there is no reset or re-enrollment path in this MVP. Preserve audit and replay history for the configured retention period and retain a non-identifying owner-slot tombstone thereafter so old proof/JTI or nonce state cannot restore eligibility. Operator CLI approves/rejects with policy version, quota and reason; approval creates the active one-to-one issuer-subject mapping only after the operator verifies the Keycloak account's `(iss,sub)` against the proof's exact Registry identity. The operator must record the verification basis and actor in the audit log. Suspension/revocation/reinstatement and mapping deactivation/remapping are explicit audited transitions. Persist enrollment/idempotency result atomically with nonce/JTI consumption; exact byte-identical proof retry with the same key returns the saved response, while changed-content or cross-owner replay is rejected. Exact nonce lifetime, maximum proof lifetime, clock skew and error mapping are required operator settings; missing settings prevent startup. Permit only one active enrollment record per owner; additional distinct submissions conflict without exposing request state.




### Object create

- `POST /v1/objects` requires `storage:create`, an active `(iss,sub)` owner mapping, approved local enrollment, and available quota. Require `Storage-Object-Kind: generic_json|site_account_entity`; for `site_account_entity`, require `Storage-Site-Origin` as a canonical HTTPS origin; forbid `Storage-Site-Origin` for `generic_json`. These headers are caller-supplied metadata, not evidence of owner consent or authorization. Reject invalid/duplicate metadata headers and noncanonical origins. Hash and persist the exact UTF-8 JSON body bytes; metadata headers are not included in the content digest. Generate the opaque object ID. Enforce owner+digest uniqueness and one site entity per mapped owner+canonical origin across active or retained objects; logical retirement does not release the site slot. Exact retries bind the idempotency key to mapped owner, route, metadata values, precondition, and exact body bytes; changed request data conflicts. Reserve quota before streaming and atomically commit object/version, digest/site uniqueness, quota ledger, and saved response; preserve the existing crash-recovery and idempotency guarantees. No per-object grant ID or consent is consumed.
- This is Storage-owned version 1 and does not mutate the adopted ecosystem semantic-v1 package. Token role authorization and content/metadata validation are separate contracts.

## 5. Storage HTTP surface

All protected requests use the Bearer scheme in the `Authorization` header over TLS. Token transport in query strings or form bodies is rejected. Registry Provider Records remain owner-authorized and outside the Storage service's write surface: owner clients create/update/withdraw them through the Registry's current digest-keyed contract in Storage issue #4, and Storage never performs those actions automatically. Create/update responses return `provider_url` as the current-object API URL (`GET /v1/objects/{id}`), not an immutable historical-version URL. The URL is a locator, not an authorization grant; callers need the `storage:read` role and ownership mapping to retrieve the current object. After replacement, that URL resolves only the new current version; old Registry records may remain independently published but their old-digest content is not retrievable through this MVP. Owner clients are responsible for publishing a new record for a new digest and, if desired, separately withdrawing the old record; Registry reachability, stale-record cleanup, and historical-content delivery are outside this Storage MVP. Same bytes stored by different owners remain independent, but the Registry permits only one owner-authorized Provider Record per digest: Storage create success does not guarantee another owner can publish or discover that digest through the Registry. Storage never publishes or withdraws another owner's record.

- `GET /.well-known/decent-storage-provider.json`: public, read-only, version-1 provider profile. It contains only provider-wide audience/endpoints, accepted media types/parameters, request-size limits, quota accounting/downgrade policy, revocation profile and disclosed durability/backup/deletion limits; it never exposes individual owner quota or enrollment data. Operator CLI changes the published profile; this is not an admin API.
- `POST /v1/enrollment-challenges`: public and rate-limited; no Keycloak access token or Storage role is required. Request body `{}`; `201` returns `storage_aud`, unpadded base64url `nonce`, and integer `expires_at`. This route reveals no enrollment state and always returns a fresh challenge.
- `POST /v1/enrollments`: raw compact proof JWS as `application/jwt`, required `Idempotency-Key`; `202` returns opaque `request_id` and `state=pending`. Byte-identical retry with the same key returns the original result.
- `GET /v1/enrollments/me`: requires a valid access token with `storage:enrollment:read` and an active `(iss,sub)` mapping. Return only the mapped Registry owner's current state (`approved`, `suspended`, `revoked`, or `withdrawn`), policy version, decision timestamp/reason when applicable, and assigned quota only while approved. No per-request Registry resolution is performed. The operator creates the mapping at approval, so owners whose requests are pending, rejected, or never approved have no mapping and cannot query status through this route; enrollment proof submission still returns its own opaque `request_id` and `pending` receipt.
- `DELETE /v1/enrollments/me`: requires `storage:enrollment:withdraw` and an active `(iss,sub)` mapping; no object role or enrollment-state prerequisite is required. Commit withdrawal and invalidate local eligibility for subsequent object operations; already-issued tokens remain valid until their signed expiry, but local enrollment checks deny new protected operations. It does not delete objects or withdraw Provider Records.

- `POST /v1/objects`: raw UTF-8 JSON object with required `Idempotency-Key`, `Storage-Object-Kind`, and conditional `Storage-Site-Origin`; requires `storage:create`, an active owner mapping, approved enrollment, and quota. Returns `201` with server-generated ID, digest, byte count, kind, current-object `provider_url`, and profile reference. Exact retry with the same key, mapped owner, metadata, and body returns the saved response; mismatched retry returns `409`.
Object IDs are 32 CSPRNG bytes encoded as unpadded base64url (43 characters), globally unique and never reused; lookup is scoped to the owner resolved from `(iss,sub)`. Version IDs are the exact payload digest `sha256:` plus 64 lowercase hexadecimal characters. The service never accepts a caller-chosen object ID.
- `GET /v1/objects/{id}` requires `storage:read`, an active `(iss,sub)` owner mapping, approved local enrollment, and applicable object/lifecycle policy; it does not require remaining quota or quota availability. Resolve the object under the mapped raw Registry owner; `200` returns the complete current object with `object_id` and `digest`. No per-object digest, purpose, site/client, or pointer scope is checked.
- `GET /v1/objects/{id}/versions/{digest}`: not supported in this MVP; return the uniform privacy-safe `404 not_found` for every request. Retained historical versions may remain internally for the caller-selected `versioned` retention period published by the provider and remain quota-counted, but there is no API for reading them. Retired versions are never readable, including from backup.
- `PUT /v1/objects/{id}` sends a complete replacement JSON object, requires `storage:update`, `Idempotency-Key`, an active mapping, approved enrollment/quota, strong `If-Match` matching the current digest, and `Storage-Retention-Mode: atomic|versioned`. The header expresses the caller's operation choice, not authorization; bind it into the idempotency fingerprint. Object kind and site-origin metadata are immutable after creation; reject `Storage-Object-Kind` or `Storage-Site-Origin` headers on update. Validate the complete replacement against the JSON profile and local policy; no JSON Pointer authorization applies. `200` returns the new digest and current-object `provider_url`; old version bytes remain unreadable through this MVP's API even when versioned retention preserves them internally.
- `DELETE /v1/objects/{id}` requires `storage:delete`, an active owner mapping, approved enrollment, and `Idempotency-Key`. Scope object lookup to the mapped raw Registry owner. The route enters the object-retirement barrier defined in §6: it rejects new reads/mutations uniformly as `404`, waits for existing bounded reads to finish and prevents any pre-existing mutation from committing after the barrier. Only after the barrier is drained does it capture the complete retained-version set, append/verify the external tombstone if backups are enabled, and commit logical retirement. `204` means retirement committed and all versions are unavailable; after a durable journal intent, retirement cannot be rolled back and recovery completes it before serving. If barrier drain times out before any journal intent, abort the retirement and return `503`; if journal append status is uncertain, keep the object blocked until the journal's linearizable `resolve-or-fence` returns either the committed tombstone or a terminal cancellation fence; only that cancellation fence permits reopening, never a mere absence read. Physical active-copy purge follows the disclosed window; backups expire separately and may never restore retired content. Registry withdrawal remains separate.
- Resource-retry ordering is security-sensitive: first verify access-token signature/issuer/audience/expiry and role claim, resolve its exact `(iss,sub)` mapping, and check current local enrollment/quota/object policy for the route; enrollment proof submissions instead validate the JWS and current Registry identity before replay handling. Then compute the exact request fingerprint and look up the owner-scoped idempotency key. A completed exact retry returns its saved response before checking changed current object state; changed body, route, metadata, precondition, or owner conflicts. A withdrawal retry may return its saved `204` for the same mapped owner even when local state is already withdrawn. New requests then check current object/state and start a reservation. There is no per-object grant JTI or assertion replay state.
- Every mutation except challenge creation requires `Idempotency-Key`, bound to mapped Registry owner, method, route/object ID, exact body digest, metadata (including `Storage-Retention-Mode`), and relevant precondition. `If-Match` mismatch returns `412 precondition_failed`; missing Bearer credentials return `401` with a bare challenge; supplied invalid tokens, inactive/missing mappings, malformed role arrays, duplicate/unknown roles return privacy-safe `401 invalid_token`; a valid token with an absent Storage role set or without the route role returns `403 insufficient_scope`; absent, other-owner, or retired objects share privacy-safe `404 not_found`; duplicate digest/site slot, replayed enrollment nonce/JTI not matched to the same completed idempotent request, changed idempotency request, or active in-progress duplicate returns generic `409 conflict`/`request_in_progress`; owner quota overflow is `409 quota_exceeded`; unsupported media type is `415 unsupported_media_type`; request limit is `413 content_too_large`; JSON depth/node-budget violation is `413 content_too_complex`; rate limit is `429 rate_limited`; unavailable required issuer/JWKS/Registry/enrollment/quota/storage state is fail-closed `503 upstream_unavailable`. Enrollment `application/jwt` proof errors follow §4 and are never mapped as Bearer-token errors. Errors use the fixed sanitized problem body in §3.3 and never contain owner/object identifiers. Challenge creation is separately rate-limited and always returns a new nonce.


- No object listing, automatic Registry write, or owner-data disclosure. The service never trusts owner identifiers from request headers/bodies. `Storage-Object-Kind` and `Storage-Site-Origin` are accepted only as syntactically validated metadata under §4 and never as authorization evidence. Exact response schemas are part of this spec.


## 6. Content, policy and persistence

- Account Entity JSON profile follows #11: UTF-8 RFC 8259 top-level object, schema-open, no charset parameter, duplicate member names rejected at every depth, and non-finite numbers rejected; no canonical-JSON requirement. Accept no non-identity `Content-Encoding`. Preserve accepted original bytes and SHA-256 those exact bytes; never canonicalize/re-serialize stored content. Apply the published parser budgets to every JSON document accepted or parsed by Storage, including object bodies, JWT/JWS headers and claims, provider profiles, and introspection responses: enforce `max_json_depth` (root object/array depth is 1; each nested object/array adds 1) and `max_json_nodes` (count the root and each nested object, array, and member/element value; object member-name strings are covered by byte limits). Enforce `max_request_bytes` for request bodies and `max_token_bytes` for each Bearer/JWS credential before decoding/parsing. Reject any limit violation before persistence or authorization; parsers must use bounded/non-recursive processing so hostile nesting or node counts cannot cause unbounded recursion or CPU/memory use. For requests, byte-size limit violations return `413 content_too_large`; JSON depth/node-budget violations return `413 content_too_complex`. Invalid or oversized `Authorization: Bearer` tokens return privacy-safe `401 invalid_token`; the enrollment `application/jwt` proof follows the route-specific `413`/`400`/`409` precedence in §4 and is not mapped as a Bearer token error. Provider explicitly publishes enabled media types, parameters, validators and request limits.
- JSON Pointer is not an authorization mechanism in this profile. Reads return the whole current object; updates validate a full replacement against the Storage JSON syntax/complexity contract and local policy.

- `Content-Length` is mandatory for create/update, must be positive and no greater than published `max_request_bytes`; reject compressed content. Charge exact bytes for unique retained digests per owner; cross-owner copies are charged independently, while metadata/backup overhead use provider capacity. In a short SQLite transaction, reserve the full declared bytes for every new unique digest before streaming (including atomic replacement while the prior version remains charged); a digest already retained in that same logical object reserves zero. Count committed retained bytes plus all active reservations against quota. Stream only after the reservation commits, verify actual bytes equal it, and release it on every failure or startup reconciliation of abandoned writes. At final commit, revalidate current version, digest uniqueness, quota, site slot, active owner mapping, and idempotency state; atomically switch version references, release old bytes only if no retained owner reference remains, and mark idempotency complete. Never hold a SQLite transaction open while streaming. When a full new-payload reservation plus committed retained usage exceeds current quota, deny the write even if the final atomic replacement would reduce retained bytes; there is no replacement credit. This is the Storage-consumer profile's explicit narrowing of issue #10's non-increasing-write allowance, not a semantic-v1 or ecosystem-wide change.


- On quota reduction below current retained usage, preserve data; reads and deletes remain available. New unique-byte writes are admitted only when their full reservation plus committed retained usage fits the current quota. No replacement credit applies; a smaller atomic replacement is rejected if old+new exceed the quota, even when the post-commit retained ledger would decrease. Same-digest/no-new-byte operations require no additional reservation.
- SQLite stores enrollment/operator decisions and audit, active/inactive issuer-subject-to-Registry-owner mappings, site-origin/object metadata, permanent object-ID tombstones, retained/retired version pointers, per-owner digest/quota ledger, reservations, consumed enrollment nonce/JTIs, and idempotency results. Enforce one owner+digest to one logical object across all retained versions and never delete object-ID tombstones; enforce mapping uniqueness in both directions per issuer and prevent active reassignment without an audited operator transition. Use serialized SQLite write transactions/constraints (proposed `BEGIN IMMEDIATE` plus unique constraints) so concurrent mappings, digest creation, and quota reservations have one winner.
- Proposed blob commit order: stream to private same-filesystem staging while counting/hashing; validate exact JSON profile, computed digest and quota; flush+`fsync`; install the owner-hash/digest blob path with atomic no-clobber semantics (never overwrite an existing path). If that path already exists, verify its bytes and digest before reusing it; if corrupt or mismatched, fail closed and alert without modifying it. `fsync` parent directory; then commit the SQLite object/version/quota/idempotency transaction. Do not expose a version until payload durability and metadata commit succeed. A blob referenced by any committed metadata is immutable and must never be replaced or deleted by retry/reconciliation. On crash before DB commit, the old current version remains; orphan cleanup must first prove no committed metadata references a blob. On crash after DB commit but before response, an exact authorized retry reads back and returns the committed idempotency result.
- Existing-object reads and mutations use a per-object concurrency barrier independent of long-lived SQLite transactions. Every read acquires a lease only while metadata is `active` and retains it through completion of the response; every object mutation acquires a lease while active and must recheck `lifecycle=active` plus the captured lifecycle generation in its final commit transaction. A single SQLite transaction changes `active -> retirement_preparing`, records a unique retirement operation ID, and prevents new read/mutation leases; later mutations cannot commit. Existing bounded reads drain; pending mutations either committed before the barrier transaction (and are included) or fail their final state check and release reservations. Do not enumerate the version set or append a deletion tombstone until all prior leases have drained. If draining exceeds the configured operation bound, clear the barrier only when no journal append could have occurred, then return `503`; if append status is uncertain, leave the object blocked until the journal atomically resolves the operation ID to a committed tombstone or terminal cancellation fence.
- Once prior leases drain, capture every retained version digest under the barrier. When backups are enabled, append an idempotent tombstone keyed by the persisted retirement operation ID and containing that complete version set; no object/version may be added or committed after capture. A successful append is irreversible deletion intent. On timeout or ambiguous append result, call the journal's linearizable `resolve-or-fence(operation_id)`: it returns the committed tombstone if append won, otherwise durably records a terminal cancellation fence that rejects every delayed/current/future append for that ID. A mere `absent` read is never sufficient to reopen the object. If resolution is unavailable, keep the object blocked and return `503`. Once the tombstone is committed, set local lifecycle to `retired` and commit all-version retirement, quota changes and idempotency result. If that SQLite commit fails, keep the barrier and immediately reconcile/retry retirement before serving another request for that object; until the local retirement commits, reject every object request with uniform privacy-safe `404` or recovery-state `503`. If in-process reconciliation cannot complete, alert the operator and serve no reads for that object. If the response fails after the metadata commit, an exact authorized retry returns the saved idempotent response. On process restart, acquire the single-node process lock, resolve every `retirement_preparing` operation ID with the same `resolve-or-fence` primitive, and reconcile before serving: a committed tombstone requires completing retirement; a terminal cancellation fence or a journal-disabled profile permits resetting the lifecycle to `active`; unresolved status keeps the object/service offline. Clear only leases proven to belong to the terminated process. This ensures no concurrent read continues after journal deletion intent and no version can be omitted from its tombstone.

- The caller selects atomic or versioned replacement using required `Storage-Retention-Mode: atomic|versioned`; this operation metadata is not authorization and is bound into idempotency. Versioned replacements retain prior versions as historical, quota-counted content until the operator-configured version-retention policy expires; historical versions are not readable through this MVP's HTTP API. Atomic replacement retires the prior version at commit. Delete retires every version. Retired versions are unavailable immediately and must never be restored from backup; backup copies expire under the disclosed schedule. Release owner quota when a digest has no retained reference, even if a private backup copy remains. Retirement releases the Storage owner+digest uniqueness constraint, so a later create may retain those bytes under a new object ID; Provider Record publication/withdrawal remains a separate owner action, and Storage makes no claim that an old Registry record is automatically withdrawn or rewritten.
- Publish a provider-specific durability/availability profile before upload/consent: storage/failure domain, backup scope/cadence/retention/expiry, tested restore expectations, recovery limits, deletion-erasure caveats and any RPO/RTO; no universal replication/SLA is implied. A static public profile or read-only well-known document is proposed; no admin API or Registry write is implied. Minimum durability is process-crash/restart on the declared tier. If backups are enabled, the deletion journal is a required separate trust/failure domain: an off-host append-only/WORM service, configured with credentials independent from the Storage host and backups, durably assigns monotonic sequence numbers, authenticates its current head, supports idempotent append plus a linearizable `resolve-or-fence(operation_id)` primitive, and retains all committed tombstones and cancellation fences for the deployment lifetime. For each operation ID, append and resolve-or-fence race atomically: the sole terminal outcome is either a committed tombstone (containing the complete retired version set) or a durable cancellation fence; if the fence wins, every delayed or future append for that ID is rejected, while if append wins the resolver returns the tombstone. A plain absent/status read never authorizes reopening. Tombstones and cancellation fences contain only opaque operation/object identifiers, version digests where applicable, sequence and authenticated chain data—never owner identifiers or payload. Before committing retirement in SQLite, Storage must durably append and verify the tombstone. If `resolve-or-fence` returns a committed tombstone, keep the barrier and complete retirement; if it returns a terminal cancellation fence, reset to active and return `503`; if the resolver is unavailable or the outcome remains unknown, keep the object blocked and return `503`. The journal tombstone is authoritative deletion intent: if the SQLite commit fails, the still-running process reconciles it immediately while keeping the object blocked; if the process crashes after append, startup reconciles and completes retirement before serving, even if the request did not receive a success response. Each backup records its last included journal sequence. Restore must fetch and authenticate the independent latest journal head, prove continuity from the backup's checkpoint through that head, replay all tombstones and verify payload/ledger references before opening the service to traffic. A missing, stale, rolled-back, unverifiable or incomplete head/chain means remain offline and fail closed; never restore the journal from the same backup or allow an older backup to replace it. The provider profile is truthful only when these controls are in force; otherwise `backup.enabled=false`, all backup numeric fields are null, the journal mode is `none`, and restore is unsupported. No at-rest privacy, HA, host-loss recovery or cross-volume atomicity claim without separate evidence.

## 7. Authorization/revocation and privacy

- The sole supported revocation profile is `normal_expiry`. Storage validates token expiry and the active subject mapping on every request, plus current local enrollment/object policy and quota admission for creates/writes. It does not call RFC 7662 introspection, resolve Registry identity on every request, or promise immediate revocation after role removal, account changes, or enrollment withdrawal. Previously issued tokens remain usable for their roles until signed `exp`, except current local policy still denies operations when required. No Storage-side maximum token lifetime or maximum revocation delay is defined; the issuer/operator controls access-token and refresh lifetimes.
- For object-data requests, verify the access JWT, resolve exact `(iss,sub)` through an active owner mapping, require the route role, and check current local enrollment/object state. Apply quota availability checks to creates and writes; reads and deletes remain available to approved owners even when retained usage exceeds a reduced quota. Enrollment status/withdrawal uses the active mapping and its respective role but does not query Registry or require approved enrollment/quota. Enrollment proof submission remains independent: validate its Ed25519 JWS and current Registry identity/key/sequence before consuming nonce/JTI. Role removal affects newly issued/refreshed tokens according to ordinary Keycloak policy; already-issued tokens are not revoked before `exp`.
- Bound each operation by published body-size limits, required `Content-Length`, a configured `max_operation_duration_seconds`, and bounded concurrent-request limits. Local entitlement withdrawal/suspension/revocation after a request's local authorization check may allow only that one already-authorized bounded atomic operation to finish; it cannot extend to another operation, range/chunk session, or continuing stream without fresh checks. No partial object becomes readable before commit. This is an operation race boundary, not immediate token revocation.
- The owner no longer selects access to JSON fields through JSON Pointers: `storage:read` returns the complete current object and `storage:update` permits a full replacement, subject to structural validity, `If-Match`, idempotency, quota, and lifecycle barriers.
- Missing credentials: 401 with a bare Bearer challenge; supplied invalid token, inactive/missing mapping, malformed/duplicate/unknown role claims: privacy-safe 401 `invalid_token`; valid token with no Storage role or without the route role: 403 `insufficient_scope`; absent, other-owner, retired or unavailable object/version: one uniform privacy-safe 404; same-owner duplicate-digest create conflict: generic 409 with no existing object ID; required current local state unavailable: fail-closed 503. Do not reveal owner/object existence to a caller. Protected responses use `Cache-Control: no-store`; never log tokens, raw identifiers, or object content.
- TLS is required at the external boundary. Deployment must prevent direct plaintext bypass of the TLS terminator.

## 8. Operator, deployment, tests and exclusions

- `storage-admin` operates on the configured SQLite database: inspect enrollment requests, approve/reject with quota/policy version/reason, create/deactivate/remap the issuer-subject-to-Registry-owner mapping with verification evidence, suspend/revoke/reinstate, and audit each transition. CLI access is local OS authorization; no public admin HTTP API.
- Initial deployment is one Linux host/node with a persistent private blob filesystem and SQLite metadata store on that node. Packaging may be a process or container; the contract makes no HA, replication, cross-host atomicity or host-loss recovery claim.
- Test seam: exercise the public HTTP contract with a real file-backed SQLite database and temporary filesystem volume; drive issuer/JWKS, subject-owner mapping, Registry enrollment proof, local policy, and clock through deterministic boundary adapters. Do not require live external systems for the core suite or assert private helper call sequences. No production HTTP application exists yet; choose the framework during implementation without changing this external contract.
- Tests: token validation (trusted issuer/signature/JWKS, allowed algorithm/key pairing, exact single Storage audience, required `sub`/`exp`/`iat`, not-before, ID-token rejection, size/depth bounds, rotation/outage); exact role extraction only from `resource_access.<storage-client-id>.roles`, with missing/invalid/malformed/duplicate/unknown roles and roles from realm/other-client claims denied; one-to-one mapping creation/approval/audit, cross-issuer separation, duplicate/conflicting mapping rejection, inactive/missing mapping denial, explicit audited remap/deactivation, and no email/alias/key-equality linking; each role's route matrix, including valid role on another owner's object, missing route role, multi-role combinations, and unknown role mixed with known role; local enrollment/quota/object-policy checks for pending, rejected, suspended, revoked and withdrawn owners; status/withdraw route behavior for pending/rejected/never-approved subjects without mappings and approved/mapped subjects; reads/deletes remaining available after quota reduction while unique-byte writes are denied; full-object read and full valid replacement, invalid JSON rejection, `If-Match`, `Storage-Retention-Mode` and idempotency binding; create metadata header combinations, canonical origin validation, metadata spoof/change controls and owner/site uniqueness; owner-signed enrollment JWS without Bearer/role, current Registry proof, route-specific error precedence (`413` size/complexity before malformed proof, `409` replay), mapping established only after audited operator verification; role removal, refresh, expired token and explicit behavior that existing tokens remain valid until issuer `exp` with no Storage maximum revocation bound; enrollment state transitions, quota/digest/site uniqueness, crash recovery, idempotency and lifecycle barriers; UTF-8/duplicate JSON keys, quota reservation, concurrency, backups and deletion journal; HTTP TLS/header/error/no-store/privacy behavior. Run the Storage consumer suite against pinned semantic-v1 package revision `5fa46362dea1c7b1f53a27df3f5fc0a60556d1ef` and its 20 vectors only where semantic-v1 remains an independently required ecosystem contract; this RBAC profile does not consume semantic-v1 grants. This does not qualify the Keycloak implementation, WordPress consumer or ecosystem aggregate; issue #44 remains an independent open live-qualification gate.

- First-release exclusions: any Master Account Entity Storage handling—the entity remains wallet-only and outside Storage scope, including no plaintext or ciphertext copy (not merely deferred); binary/other media types; multi-node/HA; public admin API; automatic Provider Record publication/withdrawal; RFC 9068 conformance; production at-rest encryption/availability promises; unsupported issuer claim translation; global exactly-once replay guarantees.
