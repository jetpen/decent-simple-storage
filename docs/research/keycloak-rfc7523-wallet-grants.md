# Keycloak RFC 7523 wallet-grant feasibility

**Research ticket:** [#16 — Research Keycloak extension feasibility for wallet-signed grants](https://github.com/jetpen/decent-simple-storage/issues/16)
**Preceding decision:** [#15 — Use Keycloak JWT Authorization Grant without a Storage callback](https://github.com/jetpen/decent-simple-storage/issues/15)
**Keycloak release examined:** 26.8.0 (versioned official docs/API and source tag).
**Scope:** Feasibility of the selected client-to-Keycloak RFC 7523 exchange plus an installable Keycloak extension. This report does not change the selected trust boundaries or claim that a prototype exists.

## Executive finding

**The selected flow is technically plausible as an installable extension, but is not expressible by stock RFC 7523 configuration alone and is not yet proven end-to-end.** Keycloak 26.8 supports the JWT Authorization Grant at the standard token endpoint. Its trust-provider extension hook can receive the assertion during grant processing; an implementation can add the wallet-signature checks and current exact-match Identity/Registry lookup required by the decisions. However, Keycloak 26.8 places the relevant `JWTAuthorizationGrantProvider` contract under `server-spi-private`; the general custom OAuth grant SPI is also explicitly internal. The security-critical custom behavior therefore depends on version-specific, unstable Keycloak APIs.

There are two additional proof obligations beyond verification:

1. Keycloak resolves an assertion `sub` through a pre-existing federated identity link, so the chosen raw identifier can be used as the external subject if that exact string is provisioned as the link's external user ID. No alias/key-equality inference is needed. But a Keycloak-issued access token is minted from the local Keycloak user; 26.8's transient token builder initially sets access-token `sub` to the local `UserModel` ID. If Storage must see the raw identifier in the **access-token** `sub` (as opposed to the external assertion `sub`), a separately verified mapper/extension behavior is needed.
2. Keycloak does not document that arbitrary resource-specific claims in the grant assertion are copied into its access token. The 26.8 source uses the provider result to find the linked user and builds a new access token from that user/session with configured protocol mappers. The assertion's object digest, Storage resource audience, actions, purpose, consent ceiling and current-key/Registry binding must be explicitly and securely propagated; stock configuration must not be assumed to preserve them.

**Recommendation:** prototype the selected grant on a pinned Keycloak 26.8.0 image, using a custom JWT Authorization Grant Identity Provider for wallet/current-Identity validation and the narrowest separate claim-mapping path that can safely preserve per-grant values. Do not add a Storage callback or change the user-selected extension direction. The prototype must establish raw external-subject linking, the actual access-token claim profile, one-use replay behavior, and fail-closed Registry handling before the design is called feasible for production. If safe dynamic-claim propagation requires overriding the whole grant, that is possible in principle but uses the explicitly internal `OAuth2GrantType` SPI; report that as an increased compatibility/security cost, not a reason to silently fork.

## Settled inputs retained

This research treats the following as fixed input from Storage #15 and the user: no custom AS↔Storage interface or Storage callback; preserve the AS-side wallet-grant validation and current Identity/Registry validation; use Keycloak's client→AS RFC 7523 grant endpoint; external assertion `sub` is the exact raw `decent-identity` identifier and is linked one-to-one to a local Keycloak user; no refresh token (a new wallet-signed grant is required after expiry); Storage receives no issuance callback and checks token scope plus current owner entitlement, object state and quota on every protected request. This report assesses feasibility of that profile; it does not reopen these choices.

The signed wallet authorization is not a Keycloak access token. It must be validated as an assertion at the AS, and Keycloak emits its own access token. The Storage service remains the resource server and must not treat successful token issuance as proof of present enrollment, quota, object existence, or permission beyond the wallet-signed scope.

## Evidence and implications

### 1. RFC 7523 layer

[RFC 7523 §§2.1 and 3.1](https://www.rfc-editor.org/rfc/rfc7523.html) defines the authorization-grant form POST with `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` and one JWT `assertion`. The assertion carries `iss`, `sub`, `aud` and `exp`, and is signed or MAC-protected. The AS validates the issuer, intended audience and signature. The RFC says this uses an existing trust relationship without a direct user-approval step at the AS; client authentication is separate and policy-dependent. It explicitly leaves how the client obtains the JWT out of scope. Consequently, RFC 7523 is a transport/grant profile, not a wallet-consent protocol, current Registry validator, or resource-access-token format.

### 2. Keycloak built-in grant layer

Keycloak's [JWT Authorization Grant guide](https://www.keycloak.org/securing-apps/jwt-authorization-grant) and [26.8 Javadocs](https://www.keycloak.org/docs-api/26.8.0/javadocs/org/keycloak/protocol/oidc/grants/JWTAuthorizationGrantType.html) document a confidential-client grant to the token endpoint. A configured Identity Provider supplies issuer and signature trust. The external `sub` must identify the external provider user and a federated link must already connect that identity to a local Keycloak user. Keycloak validates a single-valued Keycloak audience and `exp`; `jti`-based one-time use is the default (replay is rejected unless assertion reuse is enabled). Keycloak 26.6 release notes mark the feature supported.

Keycloak's guide further specifies no refresh token for this grant and a transient session. The token response contains a distinct Keycloak access token. That separation is compatible with the selected wallet assertion → AS token → Storage resource-server flow.

These built-in checks are not current-key discovery. The source for [`JWTAuthorizationGrantType.java` at 26.8.0](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/grants/JWTAuthorizationGrantType.java) parses the assertion, selects an Identity Provider from `iss`, delegates signature/assertion verification to that provider, checks assertion activity, then looks up a federated user and generates a fresh access token. Its validator does not call decent-identity or the Registry. A valid configured JWKS signature therefore cannot stand in for the required live, exact-match Identity/Registry check.

### 3. Candidate extension boundary and support status

The smallest apparent validation hook is a custom `IdentityProviderFactory`/provider implementing the 26.8 `JWTAuthorizationGrantProvider` contract. Its `validateAuthorizationGrantAssertion` receives the `JWTAuthorizationGrantValidationContext` and returns a `BrokeredIdentityContext`; the built-in grant calls it while processing the standard token endpoint request. A provider can, in principle, check the wallet signature/consent statement and perform current Identity/Registry resolution before returning a brokered external ID. This avoids adding a Storage callback and avoids replacing the grant endpoint.

But the version-pinned interface is located in Keycloak's [`server-spi-private` source](https://github.com/keycloak/keycloak/blob/26.8.0/server-spi-private/src/main/java/org/keycloak/broker/provider/JWTAuthorizationGrantProvider.java), not a stable protocol contract. The base `IdentityProviderFactory` is also in private server SPI code. The source contract accepts a grant-validation context and returns brokered identity; it does **not** promise dynamic wallet-claim copying into the issued access token.

For full custom grant processing, Keycloak 26.8 exposes `OAuth2GrantType`/`OAuth2GrantTypeFactory` and `OAuth2GrantTypeSpi`; its [26.8 release notes](https://www.keycloak.org/docs/26.8.0/release_notes/) explicitly call the OAuth Grant Type SPI an internal update, and the tagged [`OAuth2GrantTypeSpi.java`](https://github.com/keycloak/keycloak/blob/26.8.0/server-spi-private/src/main/java/org/keycloak/protocol/oidc/grants/OAuth2GrantTypeSpi.java) implements `isInternal()` as `true`. This could provide more control over validation, linking and claim construction, but increases coupling to Keycloak internals. Neither route demonstrates an API support guarantee; pin, rebuild and test on every supported Keycloak release.

The official [provider packaging guide](https://www.keycloak.org/docs/26.8.0/server_development/#_providers) describes JARs under `providers/` plus `kc.sh build`/non-optimized startup. The official Keycloak 26.8 container uses OpenJDK 21. Installability is therefore a packaging fact, not a stability/security assurance.

### 4. Subject linking and claim propagation

The tagged grant source builds `FederatedIdentityModel(identityProviderAlias, brokeredIdentityContext.getId(), ...)`, then asks Keycloak for a user associated with that federated identity. Therefore the external subject can be the exact raw identity identifier if the custom provider returns that exact value as the brokered identity ID and provisioning creates a one-to-one link under the same provider alias and external ID. This does not imply normalization or alias resolution; reject any mismatch. Keycloak's federated-link data model explicitly carries provider alias and external user ID ([26.8 `FederatedIdentityModel` API](https://www.keycloak.org/docs-api/26.8.0/javadocs/org/keycloak/models/FederatedIdentityModel.html)).

Do not conflate that assertion subject with Keycloak's issued access-token subject. In [26.8 `TokenManager.initToken`](https://github.com/keycloak/keycloak/blob/26.8.0/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java), the transient-session branch initializes `sub` using `user.getId()`. That behavior is likely to apply to this grant, because its source creates a transient user session. If the selected Storage token contract requires the raw identifier as access-token `sub`, verify an explicit mapper override against the actual signed JWT; the default is the local Keycloak user ID.

For the resource authorization claims, Keycloak's built-in token builder creates a Keycloak-signed access token from the linked local user and client/session context, then runs OIDC protocol mappers. It does not copy all claims from the incoming wallet assertion. The default grant provider result's `id` is used for the federated-link lookup; the grant source does not map arbitrary wallet claims such as object digest, action, purpose, consent ceiling or current key/Registry binding into the access token. A profile mapper can add claims, but a safe per-request data path from the verified assertion to that mapper has not been established here. The prototype must prove this using exact issuance calls; simply enabling the built-in RFC grant, configuring JWKS and choosing scopes does not prove it. If the custom grant must own token construction to preserve claims safely, classify it as an internal SPI implementation and test it as such.

The assertion `aud` should target Keycloak alone under Keycloak's documented single-audience rule. The Storage audience/resource must be a separate, signed, verified, exact-Storage-instance claim in the wallet authorization and in the issued token; Storage checks its own configured issuer and resource instance. This claim name and token wire schema are outside this feasibility report.

### 5. Replay, expiry and Storage enforcement

Keycloak's default assertion-reuse policy plus `jti` aligns with the required one-time wallet grant. Require `jti`, short `exp`, a fixed allowed signature algorithm and issuer/key trust. Test same-assertion concurrent exchange against the real single- and multi-node deployment topology; the docs establish the default reuse policy but this research did not prove atomic replay-store behavior under all cluster/failure conditions.

The grant produces no refresh token. At assertion/access-token expiry, obtain a new wallet-signed grant after the user's explicit authorization. A new exchange revalidates the current exact Identity/Registry key state. Storage still checks every protected request for configured token issuer/signature, exact resource audience, time, object/action/purpose, revocation state if enabled, current owner entitlement/enrollment and quota/object state. No Keycloak issuance or assertion claim replaces those checks.

## Smallest acceptance prototype

1. Pin the official Keycloak 26.8.0 image/runtime (Java 21); package the provider JAR and rebuild. Record every private Keycloak API used.
2. Configure a confidential client and built-in JWT grant with a single Keycloak `aud`, required issuer, strict signature algorithm, short expiry and assertion reuse disabled. Create a Keycloak local user and explicit federated link under the configured provider alias whose external user ID is the exact raw `decent-identity` string.
3. Implement a development/test JWT grant Identity Provider that verifies the wallet-signed authorization and resolves the current exact identifier/key through the real Identity/Registry contract. Unavailable, unresolved, reassigned, ambiguous, stale or invalid key state must prevent issuance. No Storage request/callback is made.
4. Submit an authorized assertion and decode the returned Keycloak access token. Demonstrate precisely which value becomes access-token `sub`; assert exact Storage instance audience, object digest, action(s), purpose, wallet-grant `jti`, bounded lifetime/consent ceiling and current Identity/key binding. Verify those claims are produced from verified server-side extension state, not copied unchecked from request parameters or user profile. Confirm no account/profile content leaks into the token.
5. Assert no refresh token is returned. Expiry requires a fresh separately wallet-signed grant and a new current-Identity check.
6. Negative vectors: altered signature/algorithm, wrong issuer, wrong/multiple Keycloak audiences, wrong client/provider, raw identifier normalization or alias substitution, no federated link or wrong link, wrong object/resource/action/purpose, expanded consent ceiling, expired assertion, replayed and concurrently replayed `jti`, key rotation/reassignment, Registry/Identity outage. Every failure must issue no usable token. Verify Storage then enforces local entitlement/quota/object state on each request without callbacks.
7. Repeat build and conformance suite on the next supported Keycloak version before upgrading a deployment. Treat any internal API change as a release gate.

## Conclusion

No hard incompatibility was found between RFC 7523 and the selected extension/no-Storage-callback topology. The protocol is suitable as the client-to-AS starting point, while current Registry resolution and safe wallet-claim-to-access-token propagation are Keycloak extension responsibilities rather than built-in RFC 7523 behavior. The unavoidable caution is material: the most direct Keycloak extension contracts are private/internal in 26.8.0, so feasibility remains conditional on a working prototype and per-release security/conformance tests. No implementation was built or exercised as part of this research.
